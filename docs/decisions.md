# Зафиксированные решения (ADR)

Здесь собраны ключевые архитектурные решения проекта и их обоснование. Формат —
краткие записи: контекст, решение, почему. Дополняй новыми решениями по мере работы.

## 1. FastAPI REST API
- **Решение:** приложение строится как REST API на FastAPI.
- **Почему:** быстрый старт, async-поддержка, встроенная валидация (Pydantic), подходит
  для прототипа и последующего масштабирования.

## 2. LLM: OpenAI-совместимый API через LangChain
- **Решение:** генерация SQL через OpenAI-совместимый LLM-API, вызываемый через LangChain.
  Модель по умолчанию — DeepSeek V3 (не принципиально, можно заменить).
- **Почему:** облачный API LLM — без локальной инфраструктуры; совместимый формат
  позволяет менять провайдера.

## 3. Единый шлюз доступа — пакет db_mcp
- **Решение:** вся безопасность, валидация, RLS и аудит живут в отдельном пакете
  `packages/db_mcp`, который является единственным шлюзом к БД. Приложение `app`
  обращается к базе только через этот шлюз (MCP, stdio transport).
- **Почему:** единая точка контроля — проще обеспечить безопасность, аудит и
  консистентность доступа; app не имеет прямых строк подключения к данным.

## 4. Аутентификация: JWT + пароль (bcrypt)
- **Решение:** аутентификация по логину/паролю с выдачей JWT access-токена (RS256,
  подпись RSA-ключом). Учётные записи хранятся в расширенной таблице `users`
  (email/password_hash/is_active).
- **Почему:** полноценная аутентификация вместо прототипных заголовков `X-Role`/`X-User-Id`.
  Роль и идентификатор учётки (`sub`) берутся из JWT.

## 6. Роли приложения и пароли
- **Решение:** пароли ролей зафиксированы в `.env` (см. `.env.example`). Созданы роли
  `app_ro` (без PII), `app_admin` (с PII), `app_service` (служебная: аудит + auth).
- **Почему:** разделение полномочий по принципу наименьших привилегий.

## 7. uv workspace монорепо, Python 3.12
- **Решение:** проект — uv workspace с двумя пакетами (`db_mcp`, `app`); Python 3.12.
- **Почему:** разделение ответственности и зависимостей между шлюзом и приложением;
  единая точка управления зависимостями.

## 8. Доменные сущности в db_mcp, API-схемы в app
- **Решение:** доменные сущности БД (включая PII-метки) — в `db_mcp/models.py`;
  API-схемы (Role, Question, Answer, QueryMeta) — в `app/api/schemas.py`.
- **Почему:** модели БД нужны сиду и маскированию схемы; API-схемы описывают только
  HTTP-контракт.

## 9. Идентификация пользователей
- **Решение:** identity через таблицу `users`: `external_id` → `role` + `internal_id`
  (student_id/staff_id). Таблица расширена для auth: `email` (логин, UNIQUE),
  `password_hash` (bcrypt), `is_active`.
- **Почему:** позволяет связывать внешних пользователей с внутренними сущностями БД
  для RLS-контекста; новые колонки дают полноценный вход по логину/паролю.

## 10. Схема БД: normalize с faculties; specialties as-is
- **Решение:** введена таблица `faculties` (нормализация), `specialties` оставлена
  как есть. Разрешено расширять схему БД при необходимости.

## 11. Синтетические данные (сид)
- **Решение:** генератор `scripts/seed.py` на faker (`ru_RU`), детерминированный
  (seed=42), малый объём (~500 студентов), референс-дата `2026-09-15`
  (`REFERENCE_YEAR=2026`, `REFERENCE_SEMESTER=1`). Подробности — в [seed.md](seed.md).
- **Почему:** детерминированные и небольшой объём тестовых данных удобны для
  разработки и проверки RLS.

## 12. MCP 2.0 (MCPServer) вместо FastMCP
- **Решение:** сервер шлюза строится на классе `MCPServer` из mcp 2.0
  (в версии 2.0 FastMCP удалён). Зависимость в pyproject — `mcp>=2.0.0`.
- **Почему:** использование актуальной версии без пиннинга на устаревшую API;
  инструменты регистрируются через `@server.tool`.

## 13. Валидация SQL через sqlglot
- **Решение:** `validate.py` разбирает SQL диалектом PostgreSQL (sqlglot) и
  допускает единственный read-only запрос: SELECT или set-операцию
  (UNION/UNION ALL/INTERSECT/EXCEPT). Запрещены DDL/DML/COPY/SET,
  мультистейтменты, `SELECT INTO` (в любом узле дерева — у UNION клауза INTO
  лежит на первом операнде), опасные функции (pg_sleep, pg_read_file,
  nextval, pg_advisory_* и т.п.), клауза блокировки строк (FOR UPDATE/FOR
  SHARE) и любые изменяющие операции в узлах дерева (DML в WITH-выражениях/
  подзапросах); запросу гарантируется верхний лимит строк (`MAX_ROWS = 200`).
  Валидный PostgreSQL `LIMIT ALL` (безлимит) принимается: при ошибке парсинга
  `LIMIT ALL` заменяется на большой лимит, который затем зажимается до
  `MAX_ROWS` (fallback не затрагивает литералы/комментарии, парсящиеся штатно).
- **Почему:** AST-разбор надёжнее ручной проверки по ключевым словам; это
  соответствует требованию проекта «строить правильно с самого начала».
  Проверка «DML в любом узле» закрывает случай, когда корень — `SELECT`, а
  изменение данных спрятано в `WITH ... RETURNING`. Set-операции — типичный
  случай LLM-генерируемого SQL, их поддержка с зажимом верхнего LIMIT не
  ослабляет безопасность.

## 14. Пулы соединений по ролям PostgreSQL
- **Решение:** `access.py` держит по пулу asyncpg на роль БД: `app_ro`
  (applicant/student/teacher), `app_admin` (admin), `app_service` (аудит + auth +
  резолюция identity). RLS-контекст задаётся `set_config('app.role'/'app.user_id', ...,
  true)` в начале транзакции (эквивалент `SET LOCAL`, поддерживает параметры).
- **Почему:** переиспользование соединений и явное разделение привилегий;
  маскирование PII происходит на уровне прав роли.

## 15. Описание схемы из живого каталога БД
- **Решение:** `schema.py` строит описание схемы из `information_schema.columns`
  через пул той роли, для которой формируется описание: для `app_ro` PII-колонки
  и служебные таблицы не видны (нет привилегий) — маскирование на уровне БД.
  К каталогу добавляются русские описания таблиц/колонок и пометка PII
  (`SENSITIVE_COLUMNS`) для роли администрации.
- **Почему:** описание всегда актуально фактической схеме; не требуется дублировать
  список PII в нескольких местах сверх того, что уже задано грантами.

## 16. Аудит: пока только SQL, question отложен
- **Решение:** `audit.py` пишет в `query_log` роль, user_id, SQL, статус, число
  строк, ошибку и время; поле `question` остаётся NULL. Естественно-языковый вопрос
  и контексты сессий пользователей будут передаваться на следующих этапах.
  Роли `app_service` добавлен `USAGE ON SEQUENCE query_log_id_seq` (иначе INSERT
  с BIGSERIAL-id не выполняется).
- **Почему:** минимальный достаточный аудит на текущем этапе; без гранта на
  последовательность запись в журнал молча падала.
- **Уточнение (этап 4 фиксов):** `query_log.role` теперь заполняется реальной
  бизнес-ролью — роль приходит из приложения параметром
  `Gateway.execute_query(sql, user_id, role)` (не резолвится в шлюзе заново,
  без лишнего round-trip); гость → `"guest"` вместо `NULL`. Ошибка аудита
  по-прежнему проглатывается и не роняет основной запрос.

## 17. Канонический вокабуляр ролей в db_mcp (roles.py)
- **Решение:** введён модуль `db_mcp/roles.py` с каноническими enum
  `BusinessRole` (applicant/student/teacher/admin) и `DbPool` (ro/admin/audit).
  `access.py` держит единый словарь `_BUSINESS_ROLE_TO_POOL`, а `BUSINESS_ROLES`
  выводится из `BusinessRole`; убраны строковые ключи пулов, ветка
  `key == "admin"` и дублирующая проверка роли в `connection_for`.
  `Settings.dsn_for(DbPool)` — единая точка выдачи DSN по роли БД.
- **Почему:** единственный источник значений ролей исключает рассинхронизацию
  наборов ролей и маппинга; enum-типизация вместо магических строк. Приложение
  (`packages/app`) и сид (`scripts/seed.py`) переиспользуют `BusinessRole`
  вместо собственного enum `Role` (этап E2): роли в auth-схемах, `require_role`
  и демо-пользователях берутся из единого вокабуляра.

## 18. Таймаут запроса и сериализация создания пулов
- **Решение:** в начале транзакции `connection_for` помимо RLS-контекста
  ставится `set_config('statement_timeout', ..., true)` со значением
  `Settings.statement_timeout_ms` (10 с по умолчанию). Создание пула
  в `Pools._get` сериализуется `asyncio.Lock` (повторная проверка внутри),
  `close()` также выполняется под локом.
- **Почему:** без лимита тяжёлый/случайный SELECT держит соединение пула
  вечно (доступный DoS-вектор); гонка в ленивом создании пула могла создать
  два пула и утечь один. Таймаут ставится `is_local=true` — действует только
  на время транзакции и не влияет на другие соединения пула.

## 19. Формат ответа execute_query: columns + rows, numeric строкой
- **Решение:** ответ `execute_query` — `{columns, rows, row_count, truncated,
  duration_ms}`, где `rows` — массив массивов, а `columns` берётся из
  `record.keys()` (сохраняет порядок и дубли имён колонок). `Decimal`
  сериализуется строкой вместо `float`.
- **Почему:** `dict(record)` молча терял колонки при `SELECT *` из JOIN двух
  таблиц с одинаковыми именами (данные пропадали без предупреждения), а
  `float(Decimal)` терял точность больших numeric. Позиционный формат
  гарантирует 1:1 соответствие «колонка → значение»; строковый вывод numeric
  — lossless.

## 20. PK/FK в описании схемы — статически в TABLE_META
- **Решение:** первичные и внешние ключи каждой таблицы задаются статическим
  словарём в `schema.py` (`TABLE_META`: `primary_key`, `foreign_keys`), а не
  читаются из каталога БД. `describe()` добавляет их в описание схемы для LLM
  (улучшение генерации JOIN).
- **Почему:** описание схемы и так хардкодится (`TABLE_META`), а из БД остаётся
  брать только фактические колонки (маскированные под роль). `information_schema`
  не отдаёт constraints без REFERENCES-привилегии (не работает даже для
  `app_admin`), а расширять права ролей ради этого не хочется; чтение
  `pg_constraint` напрямую требовало бы ручного PII-маскирования. Статический
   словарь безопасен (содержимое контролируемо: PII-колонки не могут быть PK
   или целью FK — проверяется тестом-инвариантом) и синхронизируется со схемой
   так же, как остальные описания.

## 21. Резолюция identity в шлюзе (users.id → internal_id)
- **Решение:** MCP-инструмент `execute_query(sql, role, user_id)` принимает
  `user_id` = **номер учётки** (`users.id`, он же `sub` из JWT). Шлюз сам резолвит
  его в доменный `internal_id` (student_id/staff_id) через служебную роль
  `app_service` (`SELECT internal_id FROM users WHERE id = $1`) и ставит
  `app.user_id = internal_id` для RLS. Для этого `app_service` получает
  доступ на чтение `users`. В `query_log.user_id` пишется номер учётки
  (`users.id`). RLS-политики не меняются. Несуществующий `users.id`/NULL →
  `app.user_id` не устанавливается вовсе (настройка отсутствует —
  `current_setting(..., true)` даёт NULL) → нет доступа по RLS (безопасно, без
  ошибки). Настройку нельзя ставить в NULL: PostgreSQL хранит его в GUC как
  пустую строку, которая роняла бы политику преподавателя (`::int`).
- **Почему:** RLS требует доменный ID (student_id/staff_id), а JWT несёт номер
  учётки (`users.id`). Резолюцию удобнее и модульнее делать в шлюзе, а не в
  приложении: приложение остаётся «тонким» (передаёт `sub` как есть), вся
  «магия» identity локализована в единственном шлюзе. Резолвер выполняется через
  отдельное служебное подключение `app_service` (а не через `app_ro`/`app_admin`),
  поэтому `users` остаётся закрытой для пользовательских ролей.

## 22. LLM: конфигурируемый OpenAI-совместимый клиент
- **Решение:** генерация SQL и пересказ ответа выполняются через
  OpenAI-совместимый LLM-API (библиотека `langchain-openai`). Провайдер
  полностью настраивается через конфиг (`Settings`): `llm_base_url`,
  `llm_api_key`, `llm_model`, `llm_temperature`. Значения заполняются в `.env`.
- **Почему:** совместимый формат позволяет менять провайдера (DeepSeek, локальный
  vLLM/Ollama-прокси, OpenAI и т.п.) без изменения кода — достаточно поправить
  конфиг. Развивает ADR 2 (LLM через совместимый API), уточняя конфигурируемость.

## 23. internal_id задаёт админ при создании учётки
- **Решение:** при создании учётки (`POST /auth/users`) админ вручную указывает
  `internal_id` (student_id или staff_id). `AuthService.create_user` пробрасывает
  его в `Credentials`. JWT `sub` остаётся номером учётки (`users.id`); резолюцию
  выполняет шлюз (ADR 21). Проверки существования студента/преподавателя нет —
  неверный `internal_id` просто даёт пустой доступ по RLS.
- **Почему:** связка «учётка → студент/преподаватель» должна задаваться явно;
  ручное указание админом минимально и не требует от app доступа к данным
  студентов/персонала. Резолюция в шлюзе (ADR 21) не создаёт связь — она только
  читает её из `users.internal_id`, поэтому заполнять её должен auth/админка.
  Осознанный отказ от валидации существования на этом этапе (см. roadmap) —
  неверный ID безопасен (RLS deny-by-default), а валидацию можно добавить позже.

## 24. Конвейер /ask: ошибка шлюза без ретрая LLM
- **Решение:** в конвейере `POST /api/v1/ask` при `is_error` от шлюза db_mcp
  (невалидный/запрещённый SQL, RLS deny, таймаут) ответ возвращается
  пользователю сразу как HTTP 502 — без повторного вызова LLM. Ошибки LLM
  (`LLMError`) — тоже 502. MCP-сессия клиента шлюза поднимается лениво при
  первом запросе и закрывается при остановке приложения.
- **Почему:** MCP предлагает давать ошибку самому LLM для самокоррекции, но это
  умножает стоимость и задержку и размывает границу ответственности: шлюз уже
  провёл жёсткую валидацию (sqlglot) и вернул исчерпывающий текст ошибки.
  Пока генерация SQL не проверена на реальных данных, ретрай добавляет
  непредсказуемость без гарантии результата; при необходимости его можно
  добавить отдельным этапом. Ленивый старт MCP-клиента не поднимает шлюз в
  тестах и на старте без обращений к `/ask`.
  > **Заменено ADR 36:** тул-агент делает ограниченный и осознанный ретрай
  > (в пределах шагов цикла), а не запрещённый.

## 36. Тул-агент in-process со стримингом (стадии + токены)
- **Решение:** `POST /api/v1/ask` перестроен на **тул-агента**: LLM в цикле
  (≤ `agent_max_steps`, по умолчанию 5) сам решает, когда вызвать единственный
  тул `execute_query` (обёртка над `db.Gateway.execute_query` с identity
  пользователя), видит результат/ошибку и может **исправить SQL и повторить**.
  Маскированная схема кладётся в системный промпт; роль и identity — там же.
  Ответ — **NDJSON-поток** (`StreamingResponse`, `application/x-ndjson`):
  `status` (started/schema/retry), `query` (после каждого успешного
  `execute_query`), `token` (токены финального текста через `astream`),
  `done` (с `meta`: sql/row_count/truncated/duration_ms), `error` (терминал).
  Ошибки шлюза (`GatewayError`) возвращаются LLM как текст результата тула —
  ретрай ограничен шагами цикла (заменяет ADR 24). Гость — без токена
  (`user_id=None`).
- **Почему:** тул-агент даёт самокоррекцию и итеративное рассуждение (на
  практике LLM делает 1–2 запроса на вопрос, исправляя SQL по ошибкам шлюза).
  Стриминг токенов + стадии — понятный UX «вся генерация на виду» без
  клиентского фейка. Безопасность не меняется: тул — тонкая обёртка над
  шлюзом (sqlglot-валидация, RLS, маскирование, аудит в `db`), новых путей к
  БД нет; каждый вызов тула, включая неудачные, пишется в `query_log`.
Токены финального текста стримятся только когда модель отвечает текстом
   (без вызова тула) — `tool_call_chunks` собираются и исполняются, не утекая
   в ответ.

## 37. Rate limiting для /ask: скользящее окно in-process
- **Решение:** `POST /api/v1/ask` ограничен rate limiting. Признак (ключ) зависит
  от того, кто запрашивает: авторизованный — по `user_id` (устойчивый, не
  обходится сменой IP), гость — по IP (`request.client.host`). Лимиты
  **раздельные**: гость (главный вектор безвозмездного abuse платного LLM) —
  строже (по умолчанию 10/мин), авторизованный — мягче (по умолчанию 30/мин);
  окно — 60 с. Реализация — `SlidingWindowLimiter` в `core/ratelimit.py`
  (скользящее окно по `deque`, устаревшие метки вычищаются при каждом
  обращении — память ограничена запросами за окно). Лимитер — одиночка в
  `AppContext` (не на запрос). Параметры настраиваются в `.env`
  (`RATE_LIMIT_USER_REQUESTS`/`RATE_LIMIT_GUEST_REQUESTS`/
  `RATE_LIMIT_WINDOW_SECONDS`). Превышение → `HTTPException(429)`; отклонённые
  запросы **не пишутся в `query_log`** (это не исполнение SQL), только
  логируются в приложение.
- **Почему:** `/ask` без ограничений — главный эксплуатационный риск: любой
  (включая анонимного гостя) может бесконечно дёргать платный LLM-эндпоинт.
  In-process окно достаточно для одного процесса uvicorn (`make run`) и не
  требует внешней инфраструктуры (Redis/slowapi). Ограничение: при нескольких
  worker-процессах лимит будет per-process — расширение на Redis — отдельный
  этап при необходимости мультипроцесса.

## 38. PII по RLS-скоупу: флаг can_see_pii
- **Решение:** доступ к персональным данным студентов (PII) определяется не
  ролью строкой, а наличием RLS-скоупа: `can_see_pii = resolve_identity(user_id)
  is not None` в `AuthContext` (и в `Agent.stream`/`build_system_prompt`).
  При `True` промпт разрешает выбирать PII «только в рамках строк, доступных
  по RLS»; при `False` (гость) — прежний запрет «только обобщения и агрегаты».
  Сам RLS и схема не меняются — снимается лишь промптовый запрет, который
  противоречил уже разрешённому RLS-доступу.
- **Почему:** защита PII — техническая ответственность RLS (строку студента и её
  PII-поля видит только тот, кому она положена). Запрет в промпте «не выбирать
  PII» делал систему зависимой от следования модели инструкции, а не от
  реального скоупа: администратор мог выбрать чужую строку (RLS разрешает),
  но промпт это запрещал — неработающая комбинация. Флаг выводится строго из
  `resolve_identity` (не из роли), чтобы не ошибиться в обе стороны: без скоупа
  PII не разрешается, со скоупом — разрешается в границах RLS.

## 39. Приоритет должности в resolve_role
- **Решение:** `resolve_role` возвращает бизнес-роль по приоритету: 1) известная
  должность персонала (`teacher`/`head`/`dean`/`admin` из `staff.position`);
  2) `student` при наличии `student_id`; 3) иначе `None`. Раньше первым шёл
  `student`, и сотрудник-студент представлялся студентом.
- **Почему:** должность — более конкретное представление человека в вузе, чем
  факт учёбы; бейдж/промпт/аудит отражают её. Доступ (RLS) не меняется — скоуп
  остаётся объединением `student_id`+`staff_id`; меняется только выводимая роль.
  Fallback на `student` при неизвестной должности сохраняет студента с
  «непрофильной» должностью.

## 25. Веб-интерфейс: React SPA (Vite), без UI-фреймворка
- **Решение:** фронтенд — SPA на React 18 + Vite + react-router-dom в каталоге
  `frontend/`. Никакого UI-фреймворка: собственные токены и компоненты на
  CSS-переменных, светлая и тёмная темы, по [design.md](design.md).
- **Почему:** отдельный чистый фронтенд проще поддерживать и раздавать FastAPI;
  свои токены дают полный контроль над фирменным стилем и не тянут чужие
  дизайн-системы. Vite — быстрый dev-сервер и прокси `/api` на бэкенд.

## 26. Гостевой доступ без привязки к бизнес-ролям
- **Решение:** неавторизованный пользователь работает в отдельной гостевой
  сессии: без роли (applicant/student/teacher/admin), без селектора ролей в
  интерфейсе, с доступом только к общим агрегированным данным (бейдж «Гость»).
- **Почему:** требование «по умолчанию все могут делать запросы» при сохранении
  безопасности: гость не выдаёт себя за конкретную роль и не получает
  персональных данных.

## 27. Хранилище учёток в БД через шлюз; роль app_audit → app_service
- **Решение:** мок `InMemoryAuthStore` заменён на реальное хранилище
  `DbUserCredentialsStore`, которое читает/пишет `users` **через шлюз db_mcp**
  (новый инструмент `manage_user`) — принцип «приложение не ходит в БД напрямую»
  сохранён. Запись в `users` (и чтение) выполняется служебной ролью
  `app_audit`, переименованной в `app_service` (ведь она теперь не только аудит,
  но и auth, и резолюция identity). `app_service` получает `SELECT, INSERT, UPDATE
  ON users` + `USAGE ON SEQUENCE users_id_seq`; `DELETE` сознательно не выдаётся
  (деактивация мягкая, `is_active = FALSE`).
- **Почему:** учётные записи — данные приложения, но выносить их в отдельную БД
  на текущем масштабе избыточно, а писать в БД напрямую из app — нарушило бы
  единую точку контроля безопасности. Write в шлюзе реализован как жёстко
  параметризованные запросы (не произвольный SQL, не через read-only валидатор),
  поэтому не расширяет поверхность атаки. Раздельная БД auth остаётся опцией на
  случай мультитенантности/отдельной доменной инфраструктуры (см. roadmap).

## 28. Schema v2: 22 таблицы, роли выводятся из student_id/staff_id
- **Решение:** доменная схема переработана в v2 (22 таблицы): `faculties`,
  `departments`, `specializations`, `groups`, `students`, `positions`, `staff`,
  `subjects`, `terms`, `classrooms`, `buildings`, `lessons`, `lesson_group`,
  `marks`, `admission_*`, `users`, `query_log`. Таблица `users` **не хранит роль**:
  роль выводится динамически — наличие `student_id` даёт роль студента, а
  `staff_id` — роль из `staff.position` (teacher/head/dean/admin). `student_id`/
  `staff_id` — необязательные независимые «расширители» доступа.
- **Почему:** роль как производная величина исключает рассинхронизацию между
  учёткой и реальной должностью/статусом человека, а независимые id дают
  объединение скоупов (сотрудник, который ещё и студент).

## 29. RLS set-based: app.student_id/app.staff_id вместо app.role/app.user_id
- **Решение:** RLS-контекст задаётся **двумя независимыми GUC** —
  `app.student_id` и `app.staff_id`. Роль строкой (`app.role`) и единый
  `app.user_id` **не используются**. Политики на `students`/`marks` строят
  доступ аддитивно из этих id; скоупы зав.кафедрой/декана/администрации
  дополнительно проверяют должность (`staff.position`), чтобы преподаватель с
  заполненными department_id/faculty_id не получил скоуп кафедры/факультета.
- **Почему:** предыдущая модель сводила пользователя к одной роли и одному
  человеку (`users.id → internal_id → app.user_id`), что требовало «странной»
  конверсии и не отражало независимость студенческой и кадровой идентичности.
  Set-based подход: шлюзу не нужно знать роль — он ставит id, БД сама выводит
  скоуп; пользователь с обоими id автоматически получает объединение.

## 30. Отказ от app_admin; два пула app_ro/app_service
- **Решение:** роль БД `app_admin` **удалена**. Осталось два пула: `app_ro`
  (SELECT на все доменные таблицы; скоуп строк задаёт RLS) и `app_service`
  (users + query_log + резолюция identity). Доступ администратора
  обеспечивается политикой RLS (`staff.position = 'admin'`), а не отдельной
  ролью БД.
- **Почему:** в schema v2 нет колоночного сокрытия PII на уровне грантов
  (видимость PII задаёт RLS: кто видит строку студента, тот видит и её PII),
  поэтому `app_admin` как «роль с большими правами» стала избыточной. Два пула
  проще и исключают дублирование привилегий.

## 31. PII студентов: видимость через RLS, без колоночных грантов
- **Решение:** PII-поля студентов (`name`, `surname`, `patronymic`) видны всем
  ролям БД на уровне колонок; их доступность задаётся **строками RLS** — кто
  видит строку студента, тот видит и её PII. Гостю таблица `students` (и
  `marks`) недоступна вовсе.
- **Почему:** требование «имена и фамилии студентов видно студенту (свои) и
  преподавателю (своих групп) и т.д.» выполняется естественно на уровне RLS;
  отдельное колоночное сокрытие не требуется, а маскирование описания схемы
  для LLM остаётся на уровне шлюза (уровень app/db будет перестроен под эту
  модель).

## 32. Гость = абитуриент: общая информация без роли
- **Решение:** роль «абитуриент» в отдельную сущность **не вводится**. Гость —
  запрос без `user_id` (или пользователь без `student_id`/`staff_id`): RLS
  deny-by-default на `students`/`marks`, открыты только общие таблицы
  (факультеты, направления, группы, расписание, приёмная кампания, статистика
  приёма).
- **Почему:** сценарий абитуриента из [roles.md](roles.md) (направления,
  бюджетные/платные места, статистика прошлых лет, сроки подачи) покрывается
  открытыми общими таблицами без отдельной роли и без специального
  RLS-контекста.

## 33. Пакет db вместо db_mcp: библиотека вместо MCP-сервера
- **Решение:** пакет `db_mcp` переименован в `db` и перестроен как обычная
  библиотека. Приложение вызывает фасад `db.gateway.Gateway` напрямую
  (in-process), без MCP-сервера/подпроцесса: `get_schema(user_id)`,
  `execute_query(sql, user_id)`, `resolve_identity`/`resolve_role`, CRUD учёток.
  `roles.py` удалён (роль — производная величина), контракт — pydantic-модели
  (`Identity`, `QueryResult`, `SchemaDescription`, `UserRecord`). MCP-обёртка
  удалена и может вернуться как опциональный модуль, если понадобится вынести
  шлюз в отдельный процесс (tool-based агент) — но ядро про MCP не знает.
- **Почему:** MCP-транспорт не давал ценности в монорепо — это был лишь способ
  вызова тех же функций, но с лишним процессом и JSON-сериализацией. Прямой
  вызов проще, быстрее и тестируемее, а безопасность (валидация, RLS, аудит)
  не зависит от транспорта — она в логике пакета. Роль строкой больше не нужна:
  `db` id-ориентирован, а для app-уровня есть `resolve_role`.
- **Уточнение (этап 4 фиксов):** `execute_query` теперь принимает
  `role` для журнала аудита — роль приходит из приложения и пишется в
  `query_log.role` (гость → `"guest"`); в доступе роль не участвует (см. ADR 16).

## 34. App перестроен на db.Gateway; роль резолвится на каждый запрос
- **Решение:** пакет `app` перестроен с нуля как тонкий HTTP-слой из трёх
  эндпоинтов (`/auth/login`, `/auth/users/me`, `/ask`) поверх `db.Gateway`
  (in-process, без MCP-клиента). JWT несёт только `sub` = номер учётки
  (`users.id`); роль в токен не кладётся. Идентичность и роль резолвятся на
  каждый запрос через `db.resolve_identity`/`resolve_role` (асинхронные
  auth-зависимости). `AppContext` — единый контейнер сервисов (`gateway`,
  `auth`, `agent`), инжектится через override `get_context` (единственный
  шов DI и для тестов).
- **Почему:** роль — производная величина, поэтому хранить её в токене
  неверно: должность могла смениться, учётка — быть деактивирована. Резолюция
  на каждый запрос даёт свежую роль и мгновенный 401 для деактивированных
  учёток. Прямой вызов `Gateway` убирает MCP-клиент и JSON-сериализацию
  (развивает ADR 33). Единый `AppContext` упрощает тестирование — один
  override вместо россыпи подмен.

## 35. Гость работает с реальным бэкендом; учётки ведутся вне приложения
- **Решение:** `POST /ask` принимает запросы без токена (`get_optional_context`
  → `user_id=None`) — гость получает реальные данные общих таблиц через `db`
  (продолжение ADR 32). Учётные записи и связки `student_id`/`staff_id`
  заводятся вне приложения (сид / вручную в БД): в app **нет** управления
  учётками (`/users` CRUD), bootstrap-админа и `require_role`. «Админ» — это
  роль доступа по RLS (видит все строки), а не административная панель.
- **Почему:** гостевой сценарий уже поддержан шлюзом (`user_id=None`), поэтому
  локальный mock — только фолбэк при недоступном бэкенде (подключение гостя к
  `/ask` во фронтенде — отдельный этап). Управление учётками — операционная
  задача вне продукта: приложение не должно писать в БД, кроме read-only
  запросов через шлюз; сокращение поверхности и кода.
