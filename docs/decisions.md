# Зафиксированные решения (ADR)

Здесь собраны ключевые архитектурные решения проекта и их обоснование. Формат —
краткие записи: контекст, решение, почему. Дополняй новыми решениями по мере работы.

## 1. FastAPI REST API
- **Решение:** приложение строится как REST API на FastAPI.
- **Почему:** быстрый старт, async-поддержка, встроенная валидация (Pydantic), подходит
  для прототипа и последующего масштабирования.

## 2. LLM: OpenAI-совместимый API через LangChain
- **Решение:** генерация SQL через OpenAI-совместимый LLM-API, вызываемый через LangChain.
  Модель по умолчанию — DeepSeek V3 (не принципиально, можно заменить).
- **Почему:** облачный API LLM — без локальной инфраструктуры; совместимый формат
  позволяет менять провайдера.

## 3. Единый шлюз доступа — пакет db_mcp
- **Решение:** вся безопасность, валидация, RLS и аудит живут в отдельном пакете
  `packages/db_mcp`, который является единственным шлюзом к БД. Приложение `app`
  обращается к базе только через этот шлюз (MCP, stdio transport).
- **Почему:** единая точка контроля — проще обеспечить безопасность, аудит и
  консистентность доступа; app не имеет прямых строк подключения к данным.

## 4. Аутентификация: JWT + пароль (bcrypt)
- **Решение:** аутентификация по логину/паролю с выдачей JWT access-токена (RS256,
  подпись RSA-ключом). Учётные записи хранятся в расширенной таблице `users`
  (email/password_hash/is_active).
- **Почему:** полноценная аутентификация вместо прототипных заголовков `X-Role`/`X-User-Id`.
  Роль и идентификатор учётки (`sub`) берутся из JWT.

## 5. PostgreSQL 16
- **Решение:** БД — PostgreSQL 16 (образ `postgres:16-alpine`).
- **Почему:** Docker Hub был недоступен (TLS timeout), а `postgres:16-alpine` уже
  кэширован локально. 17-я версия использоваться не стала.

## 6. Роли приложения и пароли
- **Решение:** пароли ролей зафиксированы в `.env` (см. `.env.example`). Созданы роли
  `app_ro` (без PII), `app_admin` (с PII), `app_audit` (только `query_log`).
- **Почему:** разделение полномочий по принципу наименьших привилегий.

## 7. uv workspace монорепо, Python 3.12
- **Решение:** проект — uv workspace с двумя пакетами (`db_mcp`, `app`); Python 3.12.
- **Почему:** разделение ответственности и зависимостей между шлюзом и приложением;
  единая точка управления зависимостями.

## 8. Доменные сущности в db_mcp, API-схемы в app
- **Решение:** доменные сущности БД (включая PII-метки) — в `db_mcp/models.py`;
  API-схемы (Role, Question, Answer, QueryMeta) — в `app/api/schemas.py`.
- **Почему:** модели БД нужны сиду и маскированию схемы; API-схемы описывают только
  HTTP-контракт.

## 9. Идентификация пользователей
- **Решение:** identity через таблицу `users`: `external_id` → `role` + `internal_id`
  (student_id/staff_id). Таблица расширена для auth: `email` (логин, UNIQUE),
  `password_hash` (bcrypt), `is_active`.
- **Почему:** позволяет связывать внешних пользователей с внутренними сущностями БД
  для RLS-контекста; новые колонки дают полноценный вход по логину/паролю.

## 10. Схема БД: normalize с faculties; specialties as-is
- **Решение:** введена таблица `faculties` (нормализация), `specialties` оставлена
  как есть. Разрешено расширять схему БД при необходимости.

## 11. Синтетические данные (сид)
- **Решение:** генератор `scripts/seed.py` на faker (`ru_RU`), детерминированный
  (seed=42), малый объём (~500 студентов), референс-дата `2026-09-15`
  (`REFERENCE_YEAR=2026`, `REFERENCE_SEMESTER=1`). Подробности — в [seed.md](seed.md).
- **Почему:** детерминированные и небольшой объём тестовых данных удобны для
  разработки и проверки RLS.

## 12. MCP 2.0 (MCPServer) вместо FastMCP
- **Решение:** сервер шлюза строится на классе `MCPServer` из mcp 2.0
  (в версии 2.0 FastMCP удалён). Зависимость в pyproject — `mcp>=2.0.0`.
- **Почему:** использование актуальной версии без пиннинга на устаревшую API;
  инструменты регистрируются через `@server.tool`.

## 13. Валидация SQL через sqlglot
- **Решение:** `validate.py` разбирает SQL диалектом PostgreSQL (sqlglot) и
  допускает единственный read-only запрос: SELECT или set-операцию
  (UNION/UNION ALL/INTERSECT/EXCEPT). Запрещены DDL/DML/COPY/SET,
  мультистейтменты, `SELECT INTO` (в любом узле дерева — у UNION клауза INTO
  лежит на первом операнде), опасные функции (pg_sleep, pg_read_file,
  nextval, pg_advisory_* и т.п.), клауза блокировки строк (FOR UPDATE/FOR
  SHARE) и любые изменяющие операции в узлах дерева (DML в WITH-выражениях/
  подзапросах); запросу гарантируется верхний лимит строк (`MAX_ROWS = 200`).
  Валидный PostgreSQL `LIMIT ALL` (безлимит) принимается: при ошибке парсинга
  `LIMIT ALL` заменяется на большой лимит, который затем зажимается до
  `MAX_ROWS` (fallback не затрагивает литералы/комментарии, парсящиеся штатно).
- **Почему:** AST-разбор надёжнее ручной проверки по ключевым словам; это
  соответствует требованию проекта «строить правильно с самого начала».
  Проверка «DML в любом узле» закрывает случай, когда корень — `SELECT`, а
  изменение данных спрятано в `WITH ... RETURNING`. Set-операции — типичный
  случай LLM-генерируемого SQL, их поддержка с зажимом верхнего LIMIT не
  ослабляет безопасность.

## 14. Пулы соединений по ролям PostgreSQL
- **Решение:** `access.py` держит по пулу asyncpg на роль БД: `app_ro`
  (applicant/student/teacher), `app_admin` (admin), `app_audit` (запись в
  `query_log`). RLS-контекст задаётся `set_config('app.role'/'app.user_id', ...,
  true)` в начале транзакции (эквивалент `SET LOCAL`, поддерживает параметры).
- **Почему:** переиспользование соединений и явное разделение привилегий;
  маскирование PII происходит на уровне прав роли.

## 15. Описание схемы из живого каталога БД
- **Решение:** `schema.py` строит описание схемы из `information_schema.columns`
  через пул той роли, для которой формируется описание: для `app_ro` PII-колонки
  и служебные таблицы не видны (нет привилегий) — маскирование на уровне БД.
  К каталогу добавляются русские описания таблиц/колонок и пометка PII
  (`SENSITIVE_COLUMNS`) для роли администрации.
- **Почему:** описание всегда актуально фактической схеме; не требуется дублировать
  список PII в нескольких местах сверх того, что уже задано грантами.

## 16. Аудит: пока только SQL, question отложен
- **Решение:** `audit.py` пишет в `query_log` роль, user_id, SQL, статус, число
  строк, ошибку и время; поле `question` остаётся NULL. Естественно-языковый вопрос
  и контексты сессий пользователей будут передаваться на следующих этапах.
  Роли `app_audit` добавлен `USAGE ON SEQUENCE query_log_id_seq` (иначе INSERT
  с BIGSERIAL-id не выполняется).
- **Почему:** минимальный достаточный аудит на текущем этапе; без гранта на
  последовательность запись в журнал молча падала.

## 17. Канонический вокабуляр ролей в db_mcp (roles.py)
- **Решение:** введён модуль `db_mcp/roles.py` с каноническими enum
  `BusinessRole` (applicant/student/teacher/admin) и `DbPool` (ro/admin/audit).
  `access.py` держит единый словарь `_BUSINESS_ROLE_TO_POOL`, а `BUSINESS_ROLES`
  выводится из `BusinessRole`; убраны строковые ключи пулов, ветка
  `key == "admin"` и дублирующая проверка роли в `connection_for`.
  `Settings.dsn_for(DbPool)` — единая точка выдачи DSN по роли БД.
- **Почему:** единственный источник значений ролей исключает рассинхронизацию
  наборов ролей и маппинга; enum-типизация вместо магических строк. Приложение
  (`packages/app`) и сид (`scripts/seed.py`) переиспользуют `BusinessRole`
  вместо собственного enum `Role` (этап E2): роли в auth-схемах, `require_role`
  и демо-пользователях берутся из единого вокабуляра.

## 18. Таймаут запроса и сериализация создания пулов
- **Решение:** в начале транзакции `connection_for` помимо RLS-контекста
  ставится `set_config('statement_timeout', ..., true)` со значением
  `Settings.statement_timeout_ms` (10 с по умолчанию). Создание пула
  в `Pools._get` сериализуется `asyncio.Lock` (повторная проверка внутри),
  `close()` также выполняется под локом.
- **Почему:** без лимита тяжёлый/случайный SELECT держит соединение пула
  вечно (доступный DoS-вектор); гонка в ленивом создании пула могла создать
  два пула и утечь один. Таймаут ставится `is_local=true` — действует только
  на время транзакции и не влияет на другие соединения пула.

## 19. Формат ответа execute_query: columns + rows, numeric строкой
- **Решение:** ответ `execute_query` — `{columns, rows, row_count, truncated,
  duration_ms}`, где `rows` — массив массивов, а `columns` берётся из
  `record.keys()` (сохраняет порядок и дубли имён колонок). `Decimal`
  сериализуется строкой вместо `float`.
- **Почему:** `dict(record)` молча терял колонки при `SELECT *` из JOIN двух
  таблиц с одинаковыми именами (данные пропадали без предупреждения), а
  `float(Decimal)` терял точность больших numeric. Позиционный формат
  гарантирует 1:1 соответствие «колонка → значение»; строковый вывод numeric
  — lossless.

## 20. PK/FK в описании схемы — статически в TABLE_META
- **Решение:** первичные и внешние ключи каждой таблицы задаются статическим
  словарём в `schema.py` (`TABLE_META`: `primary_key`, `foreign_keys`), а не
  читаются из каталога БД. `describe()` добавляет их в описание схемы для LLM
  (улучшение генерации JOIN).
- **Почему:** описание схемы и так хардкодится (`TABLE_META`), а из БД остаётся
  брать только фактические колонки (маскированные под роль). `information_schema`
  не отдаёт constraints без REFERENCES-привилегии (не работает даже для
  `app_admin`), а расширять права ролей ради этого не хочется; чтение
  `pg_constraint` напрямую требовало бы ручного PII-маскирования. Статический
   словарь безопасен (содержимое контролируемо: PII-колонки не могут быть PK
   или целью FK — проверяется тестом-инвариантом) и синхронизируется со схемой
   так же, как остальные описания.

## 21. Резолюция identity в шлюзе (users.id → internal_id)
- **Решение:** MCP-инструмент `execute_query(sql, role, user_id)` принимает
  `user_id` = **номер учётки** (`users.id`, он же `sub` из JWT). Шлюз сам резолвит
  его в доменный `internal_id` (student_id/staff_id) через служебную роль
  `app_audit` (`SELECT internal_id FROM users WHERE id = $1`) и ставит
  `app.user_id = internal_id` для RLS. Для этого `app_audit` получает
  `SELECT (id, internal_id) ON users`. В `query_log.user_id` пишется номер учётки
  (`users.id`). RLS-политики не меняются. Несуществующий `users.id`/NULL →
  `app.user_id` не устанавливается вовсе (настройка отсутствует —
  `current_setting(..., true)` даёт NULL) → нет доступа по RLS (безопасно, без
  ошибки). Настройку нельзя ставить в NULL: PostgreSQL хранит его в GUC как
  пустую строку, которая роняла бы политику преподавателя (`::int`).
- **Почему:** RLS требует доменный ID (student_id/staff_id), а JWT несёт номер
  учётки (`users.id`). Резолюцию удобнее и модульнее делать в шлюзе, а не в
  приложении: приложение остаётся «тонким» (передаёт `sub` как есть), вся
  «магия» identity локализована в единственном шлюзе. Резолвер выполняется через
  отдельное служебное подключение `app_audit` (а не через `app_ro`/`app_admin`),
  поэтому `users` остаётся закрытой для пользовательских ролей.

## 22. LLM: конфигурируемый OpenAI-совместимый клиент
- **Решение:** генерация SQL и пересказ ответа выполняются через
  OpenAI-совместимый LLM-API (библиотека `langchain-openai`). Провайдер
  полностью настраивается через конфиг (`Settings`): `llm_base_url`,
  `llm_api_key`, `llm_model`, `llm_temperature`. Значения заполняются в `.env`.
- **Почему:** совместимый формат позволяет менять провайдера (DeepSeek, локальный
  vLLM/Ollama-прокси, OpenAI и т.п.) без изменения кода — достаточно поправить
  конфиг. Развивает ADR 2 (LLM через совместимый API), уточняя конфигурируемость.

## 23. internal_id задаёт админ при создании учётки
- **Решение:** при создании учётки (`POST /auth/users`) админ вручную указывает
  `internal_id` (student_id или staff_id). `AuthService.create_user` пробрасывает
  его в `Credentials`. JWT `sub` остаётся номером учётки (`users.id`); резолюцию
  выполняет шлюз (ADR 21). Проверки существования студента/преподавателя нет —
  неверный `internal_id` просто даёт пустой доступ по RLS.
- **Почему:** связка «учётка → студент/преподаватель» должна задаваться явно;
  ручное указание админом минимально и не требует от app доступа к данным
  студентов/персонала. Резолюция в шлюзе (ADR 21) не создаёт связь — она только
  читает её из `users.internal_id`, поэтому заполнять её должен auth/админка.
  Осознанный отказ от валидации существования на этом этапе (см. roadmap) —
  неверный ID безопасен (RLS deny-by-default), а валидацию можно добавить позже.

## 24. Конвейер /ask: ошибка шлюза без ретрая LLM
- **Решение:** в конвейере `POST /api/v1/ask` при `is_error` от шлюза db_mcp
  (невалидный/запрещённый SQL, RLS deny, таймаут) ответ возвращается
  пользователю сразу как HTTP 502 — без повторного вызова LLM. Ошибки LLM
  (`LLMError`) — тоже 502. MCP-сессия клиента шлюза поднимается лениво при
  первом запросе и закрывается при остановке приложения.
- **Почему:** MCP предлагает давать ошибку самому LLM для самокоррекции, но это
  умножает стоимость и задержку и размывает границу ответственности: шлюз уже
  провёл жёсткую валидацию (sqlglot) и вернул исчерпывающий текст ошибки.
  Пока генерация SQL не проверена на реальных данных, ретрай добавляет
  непредсказуемость без гарантии результата; при необходимости его можно
  добавить отдельным этапом. Ленивый старт MCP-клиента не поднимает шлюз в
  тестах и на старте без обращений к `/ask`.

## 25. Веб-интерфейс: React SPA (Vite), без UI-фреймворка
- **Решение:** фронтенд — SPA на React 18 + Vite + react-router-dom в каталоге
  `frontend/`. Никакого UI-фреймворка: собственные токены и компоненты на
  CSS-переменных, светлая и тёмная темы, по [design.md](design.md).
- **Почему:** отдельный чистый фронтенд проще поддерживать и раздавать FastAPI;
  свои токены дают полный контроль над фирменным стилем и не тянут чужие
  дизайн-системы. Vite — быстрый dev-сервер и прокси `/api` на бэкенд.

## 26. Гостевой доступ без привязки к бизнес-ролям
- **Решение:** неавторизованный пользователь работает в отдельной гостевой
  сессии: без роли (applicant/student/teacher/admin), без селектора ролей в
  интерфейсе, с доступом только к общим агрегированным данным (бейдж «Гость»).
- **Почему:** требование «по умолчанию все могут делать запросы» при сохранении
  безопасности: гость не выдаёт себя за конкретную роль и не получает
  персональных данных.
