# План устранения замечаний (бэкенд)

План поэтапного устранения замечаний по итогам критического разбора. Изменения —
**только бэкенд** (`packages/app`, `packages/db`), фронтенд не затрагивается.

Каждый этап выполняется по процессу проекта: реализация → `make check` →
коммит → стоп и объяснение → ожидание подтверждения на следующий этап.

## Замечания к устранению

| # | Замечание | Где |
| - | --------- | --- |
| 1 | Нет rate limiting на `POST /ask` — главный эксплуатационный риск (анонимный abuse платного LLM) | `packages/app/src/app/api/ask.py` |
| 2 | Противоречие: промпт запрещает PII, но RLS его разрешает (защита PII — чисто на доверии к промпту) | `packages/app/src/app/agent/prompts.py` |
| 3 | `resolve_role` приоритизирует `student` над должностью — администратор с обоими id представляется студентом | `packages/db/src/db/identity.py` |
| 5 | Аудит всегда пишет `role = NULL` в `query_log.role` | `packages/db/src/db/gateway.py` |

## Этап 1 — Rate limiting на `/ask` ✅ выполнено

> Реализовано: `core/ratelimit.py` (`SlidingWindowLimiter`), параметры в
> `core/config.py`/`.env.example` (`RATE_LIMIT_USER_REQUESTS`=30,
> `RATE_LIMIT_GUEST_REQUESTS`=10, `RATE_LIMIT_WINDOW_SECONDS`=60), проверка в
> `api/ask.py`, лимитер — одиночка в `AppContext`. Тесты в
> `tests/core/test_ratelimit.py` и `tests/api/test_ask.py` (429). ADR 37.

**Признак лимита (ключ)** зависит от того, кто запрашивает:

- авторизованный пользователь → по `user_id` (номер учётки из JWT) — устойчивый
  признак, не обходится сменой IP;
- гость (аноним) → по IP (`request.client.host`) — единственный доступный признак
  для анонимов (слабее: за NAT IP делят; один человек за прокси может менять IP).

**Раздельные лимиты** (гость строже, т.к. это главный вектор безвозмездного abuse):

- гость: `rate_limit_guest_requests` за окно (по умолчанию 10/мин);
- авторизованный: `rate_limit_user_requests` за окно (по умолчанию 30/мин);
- общее окно: `rate_limit_window_seconds` (по умолчанию 60).

### Решение

- Новый модуль `packages/app/src/app/core/ratelimit.py`:
  - `SlidingWindowLimiter` (по ключу): хранит метки времени запросов в `deque`
    за окно; при превышении лимита — исключение `RateLimitExceeded`;
    устаревшие метки удаляются при каждом запросе (память ограничена числом
    запросов за окно, а не за всё время);
  - хелпер `check_rate_limit(key)`.
- Новые настройки в `core/config.py` (`Settings`) + `.env.example`:
  `rate_limit_guest_requests`, `rate_limit_user_requests`,
  `rate_limit_window_seconds`.
- Лимитер — **одиночка в `AppContext`** (не создаётся на каждый запрос),
  инжектится через существующий шов DI `get_context`.
- В `api/ask.py` перед вызовом агента — проверка лимита:
  - авторизованный → ключ `user:{user_id}`;
  - гость → ключ `ip:{request.client.host}`;
  - превышение → `HTTPException(429, "Слишком много запросов")`.
- Отклонённые (429) запросы **не пишутся в `query_log`** (это не исполнение SQL),
  но логируются в приложение (logger) — `query_log` не замусоривается, факты
  abuse видны в логах.

### Защита от новых проблем

- Один лимитер на всё приложение (в `AppContext`), а не на запрос.
- Очистка `deque` от устаревших меток при каждом обращении — нет утечки памяти.
- Лимит проверяется **до** вызова агента — не тратит токены LLM.
- Ограничение in-process: при нескольких worker-процессах uvicorn лимит будет
  per-process (каждый считает отдельно). Для `make run` (один процесс) корректно.
  Документировать как ограничение; расширение на Redis — отдельный этап при
  необходимости мультипроцесса.

### Тесты

- Unit: скользящее окно — N запросов проходят, N+1-й даёт 429.
- Unit: раздельные ключи для гостя (ip) и авторизованного (user_id).

## Этап 2 — Разрешить PII тем, кому RLS открывает строку

**Признак PII-доступа** — `can_see_pii = (resolve_identity(user_id) is not None)`,
то есть «есть RLS-скоуп», а **не** роль строкой. RLS сам ограничивает, какие
именно строки видит пользователь, поэтому снятие промптового запрета не
расширяет технический скоуп.

- любой аутентифицированный пользователь с `identity != None` (в т.ч. студент —
  только свою строку, это гарантирует RLS) → PII разрешён в рамках скоупа;
- гость (`identity is None`) → PII запрещён (прежний промптовый запрет).

### Решение

- Расширить `AuthContext` (`auth/deps.py`) полем `can_see_pii: bool = False`;
  заполнять в `_resolve_auth` (через `resolve_identity != None`) и в
  `get_optional_context` (гость → `False`). Чисто бэкенд, фронтенд не трогаем.
- Расширить контракт агента: `Agent.stream(question, user_id, role, can_see_pii)`
  (`agent/agent.py`); `can_see_pii` прокидывается из `ask.py`.
- Изменить `build_system_prompt(schema_text, role, can_see_pii)`
  (`agent/prompts.py`):
  - `True`: разрешающая формулировка — PII студентов можно выбирать, но только в
    рамках доступного по правам (RLS) скоупа, не выходить за него;
  - `False` (гость): прежний запрет «только обобщения и агрегаты».

### Защита от новых проблем

- `can_see_pii` вычисляется **строго из `resolve_identity`**, а не из
  `resolve_role` (иначе можно ошибочно дать PII кому-то без скоупа или наоборот).
- Снимается только промптовый запрет; технический скоуп (RLS) не меняется —
  нового риска утечки нет, а противоречие из разбора устраняется.

### Тесты

- Unit: `build_system_prompt` — флаг `True`/`False` даёт разные формулировки.
- Unit: `resolve_identity` для гостя → `None` → `can_see_pii=False`.

## Этап 3 — Исправить `resolve_role`: приоритет должности над student

`packages/db/src/db/identity.py`, `resolve_role` (строки 65-70): сейчас первым
идёт `if student_id is not None: return "student"`, что маскирует должность.

### Решение

Порядок приоритета:

1. если есть `staff_id` с известной должностью (`teacher/head/dean/admin`) —
   вернуть должность;
2. иначе, если есть `student_id` — вернуть `"student"`;
3. иначе — `None`.

### Защита от новых проблем

- Новых значений ролей не вводится (те же `teacher/head/dean/admin/student`) —
  регресса для фронтенда/промпта нет.
- RLS по-прежнему объединяет скоупы студента и сотрудника — меняется только
  представление роли (бейдж/промпт/семантика `require_role`), а не доступ.

### Тесты

- `student_id + staff_id(admin)` → `"admin"`.
- только `student_id` → `"student"`.
- `staff_id(teacher)` без student → `"teacher"`.

## Этап 4 — Исправить аудит: писать реальную роль

Сейчас `gateway.py:88` передаёт `role=None` в аудит независимо от пользователя.

### Решение

Прокидывать роль **из приложения** (агент уже знает роль), а не резолвить её в
шлюзе заново — это не добавляет лишнего запроса через `app_service` на каждый
вызов тула:

- расширить сигнатуру `Gateway.execute_query(sql, user_id, role=...)` —
  роль пишется в `query_log.role`;
- в `api/ask.py` / агенте передавать текущую роль пользователя;
- гость → роль `"guest"` (единообразно и читаемо в `query_log`, без `NULL`);
- в `ToolExecutor` прокинуть роль в `execute_query`.

### Защита от новых проблем

- Роль приходит из уже имеющегося контекста (не доп. round-trip).
- Аудит продолжает не ронять основной запрос (ошибка проглатывается — сохранить).
- Расширение сигнатуры — единственная новая точка; обновить фейки/тесты контракта.

### Тесты

- `execute_query` с ролью → в аудите роль записана; для гостя → `"guest"`.
