# Baikal

Безопасный text-to-SQL сервис для университетской базы данных PostgreSQL.

Baikal принимает вопрос на естественном языке, превращает его в SQL-запрос,
исполняет строго через единственный шлюз доступа и возвращает понятный ответ.
Система рассчитана на студентов, преподавателей, абитуриентов и администрацию
университета — каждый видит только те данные, которые ему положены.

## Как это работает

1. Пользователь задаёт вопрос по-русски (в веб-чате или через API).
2. **Тул-агент** в цикле генерирует и исполняет SQL: LLM решает, когда вызвать
   тул `execute_query` (read-only SELECT, с лимитом строк и учётом прав
   пользователя); при ошибке шлюза агент исправляет запрос и повторяет.
3. SQL исполняется через **единственный шлюз доступа** — пакет `db`:
   жёсткая валидация, маскирование схемы под пользователя, Row-Level Security
   и аудит запросов.
4. Ответ возвращается **потоком NDJSON** (`status`/`query`/`token`/`done`):
   видны этапы работы агента и генерация финального текста по токенам.

Детали устройства — в [architecture.md](architecture.md).

## Возможности

- **Роли и RLS (deny-by-default, set-based):** роль выводится из `student_id`/
  `staff_id` пользователя; студент видит только свои оценки, преподаватель —
  студентов своих групп, администрация — всё. Гость видит общую информацию и
  публичные агрегаты по студентам (численность без персональных данных).
- **Защита персональных данных:** PII-поля студентов (имя/фамилия/отчество)
  доступны только тем, кому RLS открывает строку студента; гостю они недоступны.
- **Аудит:** каждый запрос фиксируется в `query_log` (кто, что, когда).
- **`POST /api/v1/ask`:** тул-агент (вопрос → SQL через тул `execute_query` →
  ответ по-русски); ответ стримится NDJSON.
- **Веб-интерфейс:** лендинг, чат, вход; гостевой доступ без регистрации.

## Требования

- [uv](https://docs.astral.sh/uv/) — менеджер пакетов и окружений (Python 3.12)
- Docker + Docker Compose — для PostgreSQL
- Node.js ≥ 18 — для веб-интерфейса
- `openssl` — для генерации JWT-ключей (`make certs`)

## Быстрый старт

```bash
make sync                       # установить зависимости (uv sync --all-packages)
make certs                      # сгенерировать RSA-ключи для подписи JWT (RS256)
cp .env.example .env            # настроить подключение к БД и LLM
make db-up                      # поднять PostgreSQL в docker (схема, роли, RLS)
make seed                       # заполнить базу синтетикой
make run                        # запустить приложение (FastAPI на :8000)
```

После этого откройте веб-интерфейс (см. ниже) или обращайтесь к API напрямую.

## Вход

Учётные записи создаются вне приложения (сид `make seed` даёт демо-пользователей
из [seed.md](seed.md): `demo_student@example.com`, `demo_admin@example.com` и др.,
пароль `password123`; в проде — вручную в БД). Вход по логину/паролю —
`POST /api/v1/auth/login`, он возвращает JWT access-токен (RS256), который
используется для `/api/v1/ask`:

```bash
curl -s -X POST http://127.0.0.1:8000/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"demo_student@example.com","password":"password123"}'
```

Токен несёт только номер учётки (`sub`); роль и доступ резолвятся на каждый
запрос через пакет `db` (см. [architecture.md](architecture.md)).

## Веб-интерфейс (frontend)

SPA на React + Vite. Дизайн — в [design.md](design.md).

```bash
cd frontend
npm install      # установить зависимости (первый раз)
npm run dev      # dev-сервер на :5173, /api проксируется на :8000
npm run build    # production-сборка в frontend/dist
```

В чате можно работать без входа (гостевой доступ — только общие агрегированные
данные). Когда бэкенд недоступен или у пользователя нет токена, чат отвечает
локальным mock-ассистентом (детерминированно, по данным сида).

## Развёртывание в проде

Продакшен-стек живёт в каталоге `deploy/` и состоит из двух контейнеров
(`backend` — FastAPI, `nginx` — веб-сервер). База данных **внешняя** (подключение
по ссылке к отдельному серверу), в стеке её нет. Статика фронтенда раздаётся
nginx'ом, а `/api` проксируется на бэкенд.

### Окружения: два `.env`

Проект использует **два окружения, по одному `.env` на каждое**:

| Окружение | Файл конфига | Шаблон | Команды |
| --------- | ------------ | ------ | ------- |
| Разработка | `/.env` | `/.env.example` | корневой `Makefile` |
| Продакшен | `deploy/.env` | `deploy/.env.example` | `deploy/Makefile` |

В проде `deploy/.env` — **единый файл деплоя**: он читается docker compose для
подстановки `${...}` (переменная `CERT_DIR`) и одновременно передаётся в контейнер
`backend` через `env_file: .env`. Dev-окружение (root `.env`) от проде не зависит.

### Запуск (на сервере)

```bash
cd deploy
make setup     # один раз: .env из шаблона + JWT-ключи + сборка фронтенда
nano .env      # заполнить секреты (DSN внешней БД, LLM, CERT_DIR)
make up        # docker compose up -d --build
make logs      # наблюдать
```

Обновление: `git pull && make up` (если менялся фронтенд — сначала `make frontend`).

Примечание: если раньше использовался `deploy/.env.prod`, перенесите его значения
в новый `deploy/.env` и удалите старый файл (имя `.env.prod` теперь игнорируется
git'ом).

### Одноразовая настройка внешней БД

Схему, роли, RLS и вью применяют один раз через роль `app_owner` (учётные записи
заводятся вне приложения — сид / вручную). С сервера это делает
`make -C deploy db-init` (нужен `DATABASE_URL_OWNER` в `deploy/.env`), либо
вручную:

```bash
psql "$DATABASE_URL_OWNER" -f db/01_schema.sql
psql "$DATABASE_URL_OWNER" -f db/02_roles.sql
psql "$DATABASE_URL_OWNER" -f db/03_rls.sql
psql "$DATABASE_URL_OWNER" -f db/04_views.sql
```

### Особенности

- Бэкенд — **один worker** uvicorn: rate limiting in-process (ADR 37), при
  нескольких процессах лимит считался бы per-process.
- Секреты передаются через `env_file: .env` (не зашиты в образ); JWT-ключи
  (генерируются `make setup` в `certs/`) и TLS-сертификаты (каталог `CERT_DIR`)
  монтируются volume'ами.
- Nginx слушает 80 (redirect → HTTPS) и 443, раздаёт `frontend/dist` и
  проксирует `/api` на бэкенд; `CERT_DIR` обязателен — при его отсутствии
  compose упадёт с понятной ошибкой.
- Подробные команды — в `deploy/Makefile` (`up`, `down`, `restart`, `ps`,
  `logs`, `config`, `db-init`).
