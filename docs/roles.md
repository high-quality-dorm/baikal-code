# Роли пользователей и доступ к данным

Бизнес-требования к разграничению доступа: роли пользователей, что выводимо
и что запрещено, политика в отношении персональных данных (PII).

Значения ролей (`applicant` / `student` / `teacher` / `admin`) — контракт для
JWT, таблицы `users` и RLS-контекста. Канонический список — enum `BusinessRole`
в `packages/db_mcp/src/db_mcp/roles.py`. Приложение (`packages/app`) и сид
(`scripts/seed.py`) используют `BusinessRole` как единый источник значений —
собственный enum `Role` в app отсутствует.

## Разграничение доступа и персональные данные

Разрешено выводить:

- ФИО преподавателей;
- ФИО деканов;  
- ФИО сотрудников университета

Запрещено выводить:

- персональные данные студентов;
- персональные данные абитуриентов;
- паспортные, контактные и иные чувствительные данные;
- любые данные, позволяющие идентифицировать обучающихся.

Все ответы должны предоставляться в агрегированном или обезличенном формате, если речь идёт о студентах или абитуриентах

## Пользователи системы

Абитуриенты:

- получение информации о направлениях подготовки;
- количество бюджетных и платных мест;
- статистика прошлых лет (в агрегированном виде);
- сроки подачи документов;
- средний проходной балл прошлых лет.

Студенты:

- просмотр собственной успеваемости;
- cредний балл за семестр;
- наличие академических задолженностей;
- список дисциплин текущего семестра;
- расписание занятий.

Преподаватели:

- список своих дисциплин;
- количество студентов в группах;
- средний балл по дисциплине;
- процент неаттестованных;
- учебная нагрузка по семестрам.

Сотрудники и администрация:

- численность студентов по факультетам;
- статистика приёма;
- динамика набора по годам;
- отчётность по кафедрам;
- заполняемость аудиторного фонда;
- статистика отчислений (без ФИО студентов);
- нагрузка преподавателей

Важно:
Студенты могут получать только обезличенные данные
(количество мест, перечень направлений обучения и тд).

Данные других студентов выводятся исключительно
в агрегированном или обезличенном виде.

## Служебные роли PostgreSQL (для шлюза)

Разграничение бизнес-доступа (`app_ro` / `app_admin`) и его технические детали
(колоночное сокрытие PII, RLS) описаны в [architecture.md](architecture.md).
Здесь — примечание про `app_service`:

- `app_service` — служебная роль приложения; пользователям недоступна.
  Объединяет три служебные функции шлюза: запись в журнал аудита (`query_log`),
  чтение/запись учётных записей для auth (`users`), и резолюцию identity для
  RLS-контекста (`users.id` → `internal_id`). Поэтому имеет `SELECT, INSERT,
  UPDATE ON users` и `SELECT, INSERT ON query_log`. `DELETE ON users` сознательно
  не выдаётся: деактивация учётки мягкая (`is_active = FALSE`). На доменные
  таблицы (students/staff и т.п.) прав не имеет. См. ADR 21 и ADR 27 в
  [decisions.md](decisions.md).

## Связь учётки и человека (internal_id)

- Учётная запись (`users`) связывается с реальным человеком через `internal_id`:
  для студента это `student_id` (из `students`), для преподавателя — `staff_id`
  (из `staff`). У админа и абитуриента `internal_id` может быть `NULL`.
- Связь задаёт **админ вручную** при создании учётки (`POST /auth/users`),
  указывая `internal_id`. Шлюз при исполнении запроса резолвит `users.id` →
  `internal_id` и использует его как RLS-контекст. Неверный `internal_id` не
  приводит к ошибке — учётка просто не увидит данных по RLS (deny-by-default).
