# Роли пользователей и доступ к данным

Бизнес-требования к разграничению доступа: роли пользователей, что выводимо
и что запрещено, политика в отношении персональных данных (PII).

## Модель доступа: роли выводятся, а не хранятся

В `users` **нет колонки роли**. Роль пользователя вычисляется динамически из
его связок с доменными сущностями (`student_id`/`staff_id`):

- есть `student_id` → пользователь видит себя как студента (свою строку в
  `students`, свои оценки в `marks`);
- есть `staff_id` → роль берётся из `staff.position` (`teacher`/`head`/`dean`/
  `admin`) и определяет дополнительный скоуп;
- оба поля — **независимые расширители доступа**: пользователь с обоими id
  получает объединение скоупов студента и сотрудника;
- ни одного id (или запрос без `user_id`) → **гость**: только общая информация.

Доступ на уровне строк задаётся Row-Level Security (RLS) в `db/03_rls.sql` из
двух GUC — `app.student_id` и `app.staff_id`. Роль строкой не передаётся и
единый `user_id` не вводится.

## Разграничение доступа и персональные данные

Разрешено выводить:

- ФИО преподавателей;
- ФИО деканов;
- ФИО сотрудников университета.

Персональные данные студентов (`students.name/surname/patronymic`) **не
скрываются колонками** — их видимость задаёт RLS: строку студента (а значит, и
её PII-поля) видит тот, кому эта строка положена:

- студент — только свою строку;
- преподаватель — студентов групп своих занятий;
- зав. кафедрой — студентов групп по предметам своей кафедры;
- декан — студентов своего факультета;
- администрация — всех студентов.

Гостю таблицы `students`/`marks` недоступны вовсе (deny-by-default).

Все ответы должны предоставляться в агрегированном или обезличенном формате,
если речь идёт о студентах или абитуриентах.

## Пользователи системы

Гость (без входа, нет `student_id`/`staff_id`):

- общая информация: факультеты, кафедры, направления подготовки, группы,
  сотрудники (ФИО), дисциплины, аудитории, расписание;
- количество бюджетных и платных мест;
- статистика приёма прошлых лет (агрегированно);
- сроки подачи документов;
- средний проходной балл прошлых лет.

Студенты:

- просмотр собственной успеваемости;
- средний балл за семестр;
- наличие академических задолженностей;
- список дисциплин текущего семестра;
- расписание занятий.

Преподаватели (дополнительно к общей информации):

- список своих дисциплин;
- количество студентов в группах;
- средний балл по дисциплине;
- процент неаттестованных;
- учебная нагрузка по семестрам.

Зав. кафедрой (дополнительно): то же по дисциплинам своей кафедры; студенты
групп, посещающих занятия по предметам кафедры.

Декан (дополнительно): студенты своего факультета и их успеваемость;
отчётность по факультету.

Сотрудники и администрация:

- численность студентов по факультетам;
- статистика приёма;
- динамика набора по годам;
- отчётность по кафедрам;
- заполняемость аудиторного фонда;
- статистика отчислений (без ФИО студентов);
- нагрузка преподавателей.

## Служебные роли PostgreSQL (для шлюза)

Две роли БД (принцип наименьших привилегий), см. [architecture.md](architecture.md):

- `app_ro` — единственная рабочая read-only роль: SELECT на все доменные
  таблицы; скоуп строк задаёт RLS. Служебные таблицы `users`/`query_log`
  закрыты.
- `app_service` — служебная роль приложения; пользователям недоступна.
  Объединяет три служебные функции шлюза: запись в журнал аудита (`query_log`),
  чтение/запись учётных записей для auth (`users`) и резолюцию identity для
  RLS-контекста (`users.id` → `student_id`/`staff_id`; роль персонала — из
  `staff.position`). Поэтому имеет `SELECT, INSERT, UPDATE ON users` и `SELECT,
  INSERT ON query_log`, а также чтение минимальных колонок `staff`/`positions`.
  `DELETE ON users` сознательно не выдаётся: деактивация учётки мягкая
  (`is_active = FALSE`).

## Связь учётки и человека (student_id / staff_id)

- Учётная запись (`users`) необязательно связывается с реальным человеком:
  `student_id` (из `students`) и/или `staff_id` (из `staff`). Связь задаётся при
  создании учётки.
- Это «дополнительные поля-расширители», а не обязательный маппинг: они лишь
  открывают пользователю доступ к данным соответствующего студента/сотрудника.
- Неверный/несуществующий id не приводит к ошибке — пользователь просто не
  получит соответствующий скоуп (RLS deny-by-default).
- Гость и пользователь без обоих id видят только общую информацию.
